Gamepad Plugin
==============

C++ plugin that streams a **gamepad** (USB or Bluetooth) into the standard DeviceIO path in one
layout for every pad: buttons named by position and the two sticks and triggers. It reads the pad
through `SDL3 <https://github.com/libsdl-org/SDL>`_, whose drivers and
`SDL_GameControllerDB <https://github.com/mdqinc/SDL_GameControllerDB>`_ mappings resolve each pad's
own numbering, and pushes the state at 90 Hz. Source and plugin README:
:code-file:`src/plugins/gamepad/README.md`.

Supported pads: Xbox (360, One, Series, USB and Bluetooth), PlayStation (DualShock 4, DualSense),
Nintendo Switch Pro, Steam Controller, and any pad with an SDL_GameControllerDB mapping. Validated:
Xbox 360 Controller.

This plugin follows the :doc:`add_device` pattern (FlatBuffer schema → plugin ``SchemaPusher`` →
tracker → MCAP).

Components
----------

- **Schema** — :code-file:`src/core/schema/fbs/gamepad.fbs` (``GamepadButton`` and
  ``GamepadAxis``, the standard layout; ``GamepadOutput`` / ``GamepadOutputRecord``).
- **Plugin** — :code-dir:`src/plugins/gamepad`: ``core/`` reads the pad through SDL3 and reopens it
  after an unplug; ``app/`` is the OpenXR push loop.
- **Tracker** — ``GamepadTracker``, generated at configure time from the ``gamepad`` entry in
  :code-file:`src/core/deviceio_trackers/trackers.toml`.
- **Source node** — ``GamepadSource`` turns the tracker's data into ``gamepad_buttons`` and
  ``gamepad_axes`` for retargeters.

Standard layout
---------------

Buttons are named by position, so a binding means the same on every pad:

.. list-table::
   :header-rows: 1
   :widths: 25 25 25 25

   * - ``GamepadButton``
     - Xbox
     - PlayStation
     - Nintendo
   * - ``SOUTH``
     - A
     - Cross
     - B
   * - ``EAST``
     - B
     - Circle
     - A
   * - ``WEST``
     - X
     - Square
     - Y
   * - ``NORTH``
     - Y
     - Triangle
     - X
   * - ``BACK`` / ``START`` / ``GUIDE``
     - View / Menu / Xbox
     - Create / Options / PS
     - − / + / Home

The shoulders (``LEFT_SHOULDER``, ``RIGHT_SHOULDER``), stick clicks (``LEFT_STICK``,
``RIGHT_STICK``) and D-pad (``DPAD_UP`` ... ``DPAD_RIGHT``) are buttons too. ``GamepadAxis`` is
``LEFT_X``, ``LEFT_Y``, ``RIGHT_X``, ``RIGHT_Y`` in ``[-1, 1]`` (right and up positive, as in OpenXR) and
``LEFT_TRIGGER``, ``RIGHT_TRIGGER`` in ``[0, 1]``.

Device access
-------------

On a desktop session udev grants the logged-in user access to gamepad nodes, so no setup is
needed. Without a local seat (SSH, a service, a container), add the user to the ``input`` group,
and pass the pad's ``/dev/input/event*`` node into a container.

Build
-----

Linux only. The plugin builds with the default plugin set and fetches SDL3 (zlib license) at
configure time, linking it statically with only its joystick and HIDAPI subsystems:

.. code-block:: bash

   cmake -B build
   cmake --build build --target gamepad_plugin --parallel

Usage
-----

Start the plugin with the session through ``TeleopSessionConfig.plugins``, from the copy bundled
with ``isaaccapture`` (wheel installs included), and read it with ``GamepadSource``, as
:code-file:`examples/teleop/python/gamepad_printer_example.py` does:

.. code-block:: python

   from isaaccapture.retargeting_engine.deviceio_source_nodes import GamepadSource
   from isaaccapture.teleop_session_manager import (
       BUNDLED_PLUGINS_DIR,
       PluginConfig,
       TeleopSessionConfig,
   )

   config = TeleopSessionConfig(
       app_name="MyApp",
       pipeline=pipeline_reading(GamepadSource(name="gamepad")),
       plugins=[
           PluginConfig(
               plugin_name="gamepad",
               plugin_root_id="gamepad",
               search_paths=[BUNDLED_PLUGINS_DIR],
           )
       ],
   )

The plugin reads the first connected pad, keeps it until it disconnects, and then takes the first
one again. Its name, type and USB IDs are logged when it is opened.

The plugin can also run on its own, for example on another machine pushing to the same runtime,
next to any reader of the same collection:

.. code-block:: bash

   ./install/plugins/gamepad/gamepad_plugin

Multiple pads
~~~~~~~~~~~~~

Run one plugin per pad. ``--player=N`` reads the Nth connected pad, and each plugin pushes to its
own collection, read by a ``GamepadSource`` with the same ``collection_id``:

.. code-block:: python

   plugins = [
       PluginConfig(
           plugin_name="gamepad",
           plugin_root_id=f"gamepad_{n}",
           search_paths=[BUNDLED_PLUGINS_DIR],
           plugin_args=[f"--player={n}", f"--collection-id=gamepad_{n}"],
       )
       for n in (1, 2)
   ]
   sources = [GamepadSource(name=f"gamepad_{n}", collection_id=f"gamepad_{n}") for n in (1, 2)]

Published data
--------------

The plugin pushes ``GamepadOutput`` to collection ``gamepad`` (``--collection-id`` changes it;
match it in ``GamepadSource`` / ``GamepadTracker``):

- ``buttons`` — indexed by ``GamepadButton``, 1 while held. A button the pad lacks stays 0.
- ``axes`` — indexed by ``GamepadAxis``.
- ``connected`` — whether the plugin has the pad open.

While no pad is open the plugin keeps pushing with ``connected`` false and nothing held, so a
reader never holds the last stick deflection of an unplugged pad; ``GamepadSource`` then reports
its outputs as absent. Recordings use MCAP channels ``gamepad`` and ``gamepad_tracked``.

Retargeters
-----------

``GamepadToSe3RelRetargeter`` (end-effector delta from the sticks and D-pad),
``GamepadToSe2Retargeter`` (base velocity from the sticks) and ``GamepadGripperRetargeter``
(toggle on ``WEST``) consume ``GamepadSource``. Their dead zone defaults to 0.15: an idle pad's
sticks rest up to 0.14 off center.

Device status
-------------

When ``TeleopSession`` starts the plugin, it reports device ``<plugin_root_id>/gamepad``
(``gamepad/gamepad`` by default) through :doc:`../references/device_provider_monitoring`:
``CONNECTED``, ``DISCONNECTED`` when no pad is connected for its player, or ``FAILED`` when SDL
finds the pad but cannot open it.

Troubleshooting
---------------

- **Status DISCONNECTED with the pad connected** — SDL lists a device as a gamepad only when it
  has a mapping. Find the pad's line in SDL_GameControllerDB (or write one) and set it in the
  ``SDL_GAMECONTROLLERCONFIG`` environment variable of the process that starts the plugin.
- **Status DISCONNECTED over SSH or in a container** — the user cannot read the pad's
  ``/dev/input/event*`` node; see `Device access`_.
- **The robot drifts with the pad at rest** — raise the retargeter's ``dead_zone``.

Tests
-----

``gamepad_plugin_tests`` reads SDL virtual gamepads: the standard layout, stick and trigger
ranges, a pad plugged in late, an unplug, and player selection.
